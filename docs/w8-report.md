### 三个能讲的结论

1. **BM25 单独只有 0.170，融合后 0.678** —— 两路召回互补，不是"哪个好选哪个"。
2. **重排没有稳定收益**：E4 比 E3 低 3.4pp，但 E9 比 E8 高 1.7pp（都在 ±2 题噪声内），
   延迟却是 3~4 倍 → 收益不确定 + 成本确定 = 不上。
3. **排除 release-notes 贡献 +8.5 pp**（E8 0.695 → E10 0.780）—— "磁铁文档"污染是真实存在的。

> 关于双语 BM25：它让中文工单案例从"进不了 Top10"变成 Top-1，
> hit@5 上的影响在 ±1 题内（噪声），所以保留。
> 后来发现真正的副作用是**案例污染排名**（见第八、九节），已用"案例单独一路召回"解决。

### 修正 2 的结论：失败三分法

| 类 | 数量 | 判定依据 |
|---|---|---|
| A 语料缺失 | 3 | q026/q041/q050 的英文关键词（vmmem / docker.sock / manifest unknown）在 8,794 个 chunk 中无同现 |
| B 有语料未召回 | 7 | 文档在库，Top-10 一条相关都没有 |
| C 排太后 | 4 | 第 6~8 名命中（q001/q007/q051/q057） |

**额外发现（比原问题更重要）**：工单案例 `cases/*` 出现在 **17/59 题**的 Top-5，且全部是噪声。

| 配置 | hit@5 | hit@10 | MRR | nDCG@10 |
|---|---|---|---|---|
| E10（含案例） | 0.780 | 0.848 | 0.499 | 0.577 |
| **E12（排除案例，生产默认）** | 0.780 | **0.915** | **0.540** | **0.621** |

说明案例不造成漏答，但会挤掉更好的结果。**这也修正了此前的归因**：
E10 的 MRR 从 0.553 掉到 0.491，其中约 4.5pp 来自案例污染，不是全赖双语 BM25。

### 修正 3 的结论：chunk 大小

| chunk_size | chunks | hit@5 | recall@5 | MRR |
|---|---|---|---|---|
| 256 | 10,717 | 0.750 | 0.517 | 0.506 |
| **400** | 8,853 | **0.750** | **0.528** | 0.478 |
| 600 | 7,940 | 0.700 | 0.500 | 0.480 |

结论：**600 明确变差（-5pp）；256 与 400 打平，但 256 多 20% 索引成本**。
所以 400 是"效果持平 + 成本更低"的折中——不是最优，但**有依据**了。

### 附带修的一个线上问题：Redis 挂掉时记忆层很慢

排查测试卡顿时发现：每次 `get_memory()` 都会新建 client 并 ping，
Redis 不可达时 redis-py 会重试+退避，**单次耗时 15 秒**。

修法：先用 1 秒超时的裸 socket 探测，失败立即抛；再加 30 秒熔断，
之后直接走 SQLite。实测：首次 15.15s → **1.35s**，第二次 **0.00s**。

## 十、W8.3 改为置信度驱动的三级降级

原先的触发条件是「主检索为空 / 关键词命中历史工单」。改成用户期望的**置信度驱动**：
主检索置信度低 → 补工单案例 → 仍不足 → 网页搜索。

### 第一步：先校准「置信度」到底能不能算出来

新增 [`scripts/calibrate_confidence.py`](../scripts/calibrate_confidence.py)，
用评测集里的 59 道可答题 + 6 道不可答题（`answerable=false`）做二分类校准：

| 信号 | 最佳阈值 | 可答误触发 | 不可答命中 | 准确率 |
|---|---|---|---|---|
| 向量余弦（Top-1） | 0.45~0.50 | 5/59 | **1/6** | 84.6% |
| 重排分（gte-rerank） | 0.05 | 0/59 | **0/6** | 90.8%（假象：等于全判可答） |
| Top-1 相对 Top-5 尖锐度 | 0.00 | 18/55 | 1/6 | 62.3% |

分布对比（向量余弦）：可答 median **0.631** vs 不可答 median **0.570** —— **严重重叠**。
连我们人工确认"语料确实没有"的 q050 都有 0.552，高于门槛。

**结论：在这个跨语言场景下，检索分数判断不了「知识库答不了」。**
原因很直接：那 6 道不可答题仍然是 Docker 话题内的（比如"公司 VPN 怎么配才能访问私有 registry"），
检索当然能拿到看似相关的文档。分数高低反映的是"词面/语义接近"，不是"能不能答"。

### 第二步：把触发点换成更可靠的信号

既然是"能不能答"的问题，就交给模型判断。最终实现是**三级级联**：

```
主检索（排除案例与 release-notes）
   ↓ 生成答案
模型自评"资料不足"？ ──否──▶ 结束
   ↓ 是
① search_cases 补内部工单案例 → 重新生成
   ↓ 仍自评不足
② web_search 上网搜 → 重新生成
   ↓ 仍不足
③ 如实说明没有依据
```

配置项：

| 配置 | 默认 | 说明 |
|---|---|---|
| `CASE_INLINE` | false | 案例是否参与主排序（旧行为，会污染排名） |
| `CASE_GATE_VEC_SCORE` | 0.55 | 检索偏弱时也补案例（**仅辅助**，因为分数不可靠） |
| `CASE_SUPPLEMENT_TOPK` | 3 | 补充召回条数 |

### 新增能力

- 工具从 8 个增加到 **9 个**：新增 `search_cases`（只搜案例，独立一路召回）；
- `Retriever.search` 支持 `only` 白名单 + `Hit.vec_score` 带出向量相似度（供置信度使用）；
- system prompt 明确降级顺序：**先案例、再网页、最后如实说没有**。

### 验证

```
test_search_cases_only_returns_cases         ✅ 只返回 cases/*，不混官方文档
test_unsure_answer_triggers_case_before_web  ✅ 自评不足时先调 search_cases，不直接上网
单测: 41/41（6+12+3+13+7）
```

**这次最有价值的产出不是功能，而是那张校准表**：它用数据证明了"用检索分数检测不可答"
这条路走不通，从而避免了拍一个阈值上线。

## 十一、W8.4 把"自评"升级为显式哨兵

W8.3 的降级触发靠 **关键词匹配答案文本**（"知识库中没有 / 没找到 / 资料不足"）。
问题很明显：模型换个措辞就漏判（它很爱写「知识库中**没有**」，markdown 符号还会把词拆开）。

改成**协议级标记**：

```
system prompt 规则 9：
资料不足时，必须在回答最开头单独输出一行 [[INSUFFICIENT]]，
不要解释它、不要加反引号；资料充足时不要输出。
```

### 三个实现细节

| 问题 | 做法 |
|---|---|
| 标记泄露给用户 | 最终答案统一 `_strip_mark()` 清掉；流式时**先攒够能判断开头是不是哨兵的长度再吐**，避免闪一下 |
| 模型不按格式输出 | 保留关键词匹配作为兜底（`_looks_unsure` 先看哨兵，再看关键词） |
| 判断为"不足"但重写后仍不足 | 用 `case_used` / `web_used` 两个状态位防止重复触发，最多各一次 |

### 验证

```
test_sentinel_triggers_case_and_is_stripped   ✅ 哨兵触发案例补充 + 最终答案无残留
test_stream_does_not_leak_sentinel            ✅ 哨兵拆成 3 块流式吐出也不泄露
单测: 43/43（6+12+3+15+7）
```

真实链路实测（问一个知识库完全无关的问题）：

```
[2] tool → search_knowledge("我们公司食堂几点开饭")   2084ms
[3] tool → web_search(...)   ← 模型输出哨兵 → 案例无命中 → 转网页
[4] answer  6354ms  思考: 基于检索结果生成回答（已补充网络搜索）
最终回答开头：这个问题我没法给出可靠答案，原因如下……   ← 无哨兵残留
```

### 现在的完整降级链

```
search_knowledge（官方文档，排除案例/release-notes）
   ↓ 模型答不出 → 输出 [[INSUFFICIENT]]
search_cases（内部工单案例）
   ↓ 仍不足
web_search（外部搜索，强制标注来源）
   ↓ 仍不足
如实说明"没有依据"
```

## 十二、W8.5 复核 3 道"疑似语料缺失"题，修正 1 条标注

自动归因把 3 道题判成 A（语料缺失）。逐题人工查证后，**只有 1 道是真的**：

| 题号 | 问题 | 复核结论 | 证据 |
|---|---|---|---|
| q026 | WSL2 的 vmmem 吃了十几 G 内存 | **B 召回问题** | `features/wsl/best-practices.md` L11 提到 `vmmem.exe`，L25「Limit CPU and memory usage」就是解法 |
| q041 | permission denied 连不上 docker.sock | **B 召回问题** | `engine/install/linux-postinstall.md` L39/L124 有 `groupadd docker`，即标准解法 |
| q050 | 拉镜像报 manifest unknown | **A 确认缺失** | 全库搜 `manifest unknown` / `no matching manifest` / `tag does not exist` 均 0 命中 |

**修正**：q050 标记 `answerable=false`（`data/eval_cases.jsonl` 与 `eval_cases` 表同步）。
**q026 / q041 保持可答**——它们是检索问题，改标注等于把召回问题甩给数据。

### 口径变化（必须说清）

| 口径 | 可答 | 不可答 | E10 hit@5 |
|---|---|---|---|
| 修正前 | 60 | 5 | 0.767 |
| **修正后** | **59** | **6** | **0.780** |

**+1.3pp 的提升来自分母修正，不是检索变好。** 12 个配置已全部按 59 题重跑，数字口径统一。
历史周报（w3/w4/w7.1）保留当时数字，已加"口径说明"标注。

### 为什么自动分类不可靠

初筛用"关键词是否在同一个 chunk 里同现"：q026 问 `WSL2`、文档写 `WSL`；q041 问 `docker.sock`、文档写 `daemon socket`。
改成"逐词是否出现过"后误判消失，但又把 q050 放过了（`manifest` 这个词存在）。

**结论**：自动规则只能做 B/C 拆分（B=没进 Top10，C=排 6~10），
"A 到底缺不缺语料"必须人工查证。详见 [`reports/failure_review_manual.md`](../reports/failure_review_manual.md)。
