### 标注为什么用"路径前缀"而不是 chunk id

chunk 边界会随参数变化（W4 要调 chunk size），用 chunk id 标注的话**一改参数全部标注作废**。
用文档路径前缀判定"相关"，改切片参数后评测集不用重标。

## 二、结果

| 配置 | hit@1 | hit@5 | hit@10 | recall@5 | recall@10 | MRR | nDCG@10 | 延迟 |
|---|---|---|---|---|---|---|---|---|
| E1 纯向量 | **0.333** | 0.650 | 0.800 | 0.442 | 0.572 | **0.477** | 0.541 | 196 ms |
| E2 纯 BM25 | 0.100 | 0.217 | 0.333 | 0.142 | 0.225 | 0.151 | 0.190 | **20 ms** |
| E3 向量+BM25+RRF | 0.250 | **0.733** | 0.850 | **0.508** | 0.614 | 0.436 | 0.533 | 196 ms |
| E4 E3+重排 | 0.233 | 0.667 | **0.867** | 0.481 | **0.647** | 0.437 | **0.557** | 758 ms |

### 三个反直觉的发现

**① 混合检索确实提升了覆盖率，但拉低了首位精度**

- hit@5：0.650 → **0.733**（+8.3pp），recall@5：0.442 → **0.508**（+6.6pp）
- 但 MRR：0.477 → **0.436**（−4.1pp），hit@1：0.333 → 0.250（−8.3pp）

原因：RRF 用的是**名次**，它把 BM25 召回但向量没召回的条目提上来，覆盖面变好；
但同时把向量原本排第 1 的正确结果往后推了。**"多召回" 和 "排得准" 在这里是冲突的。**

**② 重排没有提升 hit@5，反而降了 6.6pp**

- hit@5：0.733 → **0.667**，recall@5：0.508 → 0.481
- 但 hit@10：0.850 → **0.867**，nDCG@10：0.533 → **0.557**

原因：重排把**整体排序变好了**（nDCG↑、hit@10↑），但把一部分原本在前 5 的相关结果挤到了 6–10 名。
代价还很高：**延迟 196ms → 758ms（4 倍）**。

> 这直接推翻了我上次基于**单条 query** 说的"重排救了效果"。
> 一条 query 不是证据，60 条才是。这个对比本身就是 W3 最有价值的产出。

**③ BM25 在"hard"题上反而比"easy"题好**

| 难度 | BM25 hit@5 |
|---|---|
| easy | 0.105 |
| medium | 0.179 |
| hard | **0.462** |

原因：**难题里往往带英文错误码或命令**（`port already allocated`、`TLS handshake timeout`、`manifest unknown`），
BM25 对这类精确串一找一个准；简单题是纯中文口语，BM25 完全无能为力。

这也解释了为什么 E3 能比 E1 高：BM25 贡献的不是"更多结果"，而是"那些含精确串的题"。

## 三、怎么解释这些数字（面试要能说）

| 指标 | 含义 | 我们的值意味着什么 |
|---|---|---|
| hit@5 = 0.733 | 5 条结果里有至少 1 条相关 | 用户大概率能看到答案，但 27% 的题看不到 |
| recall@5 = 0.508 | 多跳题要求的多个板块被覆盖的比例 | 多跳题（0.333）明显拖后腿 |
| MRR = 0.477 | 第一个相关结果的平均名次约第 2 | 排序中等，还有优化空间 |
| 延迟 196 ms | 含一次 embedding API 往返 | 对交互式场景可接受 |

**诚实评价**：中文查英文文档、8,788 个 chunk 里命中，hit@5 0.73 属于"能用但不够好"。
headroom 主要在两处：多跳题（0.667）和 hard 题（0.538）。

## 四、W4 该做什么（按 ROI 排序）

| # | 实验 | 预期 | 依据 |
|---|---|---|---|
| 1 | **重排候选从 20 扩到 50** | hit@5 可能回到 0.73 以上 | 现在相关结果可能落在 21–50 名，重排根本没看到它 |
| 2 | **RRF 的 k 值调参**（20/60/100） | 平衡 hit@5 与 MRR | k 越大越平滑，首位精度越低 |
| 3 | **chunk size 消融**（400 vs 700） | 多跳题受益 | 多跳需要跨段拼接，小 chunk 容易丢上下文 |
| 4 | **查询改写**（中文→英文关键词给 BM25） | 提升 BM25 覆盖率 | 当前 BM25 对纯中文 query 零命中 |
| 5 | **重排只用于 Top-20 之后的兜底** | 折中方案 | 简单题用向量原序，难题才重排 |

## 五、复现方式

```bash
# 建评测集（会先校验 gold_path 是否存在）
python scripts/build_evalset.py

# 跑全部四个配置，出表
python scripts/run_eval.py --configs E1,E2,E3,E4 --top-k 10

# 只跑某个配置（其余保留上次结果）
python scripts/run_eval.py --configs E4

# 只按已有结果重出报告
python scripts/run_eval.py --report-only
```

产物：
- `reports/eval_report.md` — 人读（总表 + 按题型 + 按难度 + 逐题）
- `reports/eval_summary.json` — 机器读（累积汇总）
- `eval_results` 表 — 每次 run 的原始召回 id，可追溯
